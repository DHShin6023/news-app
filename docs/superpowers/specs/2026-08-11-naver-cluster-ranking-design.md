# 뉴스앱 — 네이버 결합 + 클러스터 단위 랭킹 설계

작성일: 2026-08-11
대상: `~/Desktop/ClaudeWork/news-app` (https://dhshin6023.github.io/news-app/)

## 1. 문제

앱이 갱신되지 않는다는 체감이 있어 운영 데이터를 측정했다. 수집 파이프라인 자체는
정상이다 — 2026-08-11 하루 20회 실행, 전부 성공. 클라이언트도 캐시를 우회하고 있다
(`news_data.json?t=…` + `cache: 'no-store'`, 서비스워커 없음). 문제는 **선택 로직이
매번 같은 기사를 고른다**는 것이다.

2026-08-11 하루치 실측 (커밋 20건 기준):

| 카테고리 | 노출 슬롯 | 고유 기사 | 회전율 | 최장 잔류 |
|---|---|---|---|---|
| cat-us | 60 | 17 | 28% | 8회 |
| cat-kr | 60 | 21 | 35% | 8회 |
| cat-coin | 60 | 19 | 32% | 12회 (~13시간) |
| cat-land | 60 | 18 | 30% | 11회 |
| cat-etc | 100 | 62 | 62% | 6회 |

### 원인

1. **관련도 순서 고정.** 2026-07-13에 "동시다발 보도의 상위 독점"을 막으려 최신순
   정렬을 제거하고 Google 관련도 순서를 그대로 채택했다. 그런데 Google의 관련도
   순위는 하루 종일 거의 변하지 않는다. `when:1d` 창 안에서 1위가 고정되므로 매
   실행마다 같은 인덱스 0번을 다시 뽑는다.

2. **pubDate 미사용.** `fetch_news.py`가 발행 시각을 파싱하지만 정렬·필터·감점 어디에도
   쓰지 않는다.

3. **중요도 판정 부재.** "어느 기사가 중요한가"를 전적으로 Google 랭킹에 위임했다.
   Google의 랭킹은 클러스터 크기와 매체 권위 기반이라 시의성에 둔하고, 국내 이슈에
   대해서는 신호가 부실하다. 실제로 부동산 카테고리 1위를 정당 논평이 11회 연속
   차지했다.

4. **실행 주기 지연 (부차적).** cron이 `*/30`이지만 GitHub Actions 무료 플랜의 스케줄
   큐 때문에 실제 간격은 48~124분(평균 약 70분)이다. 통제 불가이며, 위 1~3에 비하면
   영향이 작다.

`cat-etc`만 회전율이 두 배 높은 것은 이 선택 로직을 타지 않고 Google Top Stories
피드를 그대로 쓰기 때문이다.

## 2. 목표

- 신선도와 중요도를 **5:5** 가중으로 결합해 순위를 정한다.
- 판정은 **룰 기반**으로 한다. LLM을 순위 결정에 쓰지 않는다 (상권 큐레이션의
  「AI는 판정 금지」 원칙과 동일). 모든 점수는 숫자로 설명 가능해야 하고 회귀
  테스트가 가능해야 한다.

### 성공 기준 (배포 24시간 후 재측정)

| 지표 | 기준선 (2026-08-11) | 목표 |
|---|---|---|
| 회전율 (cat-etc 제외 4개) | 28~35% | 60% 이상 |
| 최장 잔류 (동일 링크 기준) | 8~12회 | 5회 이하 |
| cat-etc 회전율 | 62% | 유지 (하락 시 실패로 간주) |

"최장 잔류"는 **같은 기사 링크**가 연속 노출된 횟수다. 같은 사건이 다른 헤드라인으로
이어지는 것은 잔류로 세지 않는다 (§5 「노출 이력은 기사 링크 기준」 참조).

## 3. 소스 전략

Google News RSS를 `hl=ko&gl=KR`로 조회하면 결과 매체는 이미 국내 언론사다
(2026-08-11 cat-us 결과: 뉴스웍스, 다음, 네이트). 즉 Google과 Naver는 **같은 국내
매체 풀을 서로 다른 방식으로 랭킹**한다. 따라서 양쪽 상위에 모두 등장하는 사건은
어느 한쪽의 랭킹 취향이 아니라 실제로 크게 다뤄진 사건이라는 신호가 된다. 이것이
교차 검증의 근거다.

| 카테고리 | 발굴 | 네이버 역할 |
|---|---|---|
| cat-us | Google 검색 + Naver 검색 | 발굴자 |
| cat-kr | Google 검색 + Naver 검색 | 발굴자 |
| cat-coin | Google 검색 + Naver 검색 | 발굴자 |
| cat-land | Google 검색 + Naver 검색 | 발굴자 |
| cat-etc | Google Top Stories | **검증자** |

`cat-etc`만 다른 이유: Naver 검색 API는 쿼리 문자열이 필수인데 Top Stories에는
쿼리가 없다. 억지 쿼리("주요뉴스 속보")를 만드는 것은 Top Stories 도입 전의 방식으로
되돌아가는 것이므로 채택하지 않는다. 대신 Top Stories로 후보를 발굴한 뒤 각 후보
제목의 핵심어로 Naver를 재검색해 유사 기사 수를 세고, 그것을 교차 점수로 쓴다.
점수 공식은 나머지 4개 카테고리와 동일하다.

### 호출량

현재 쿼리 수는 cat-us 3개, cat-kr/coin/land 각 2개로 총 9개다.

- 4개 카테고리: 9쿼리 × 2정렬(sim, date) = 18회/실행
- cat-etc 검증: 후보 20건 = 20회/실행
- 합계 38회/실행 × 약 20회/일 = **약 760회/일**. 한도 25,000회/일 대비 여유.
  맛집 큐레이션과 키를 공유해도 문제없다.

## 4. 구조

현재 `fetch_news.py`는 137줄 단일 파일이며, 127~136줄이 모듈 최상위에서 즉시
실행된다. import만 해도 네트워크 호출이 일어나므로 단위 테스트를 쓸 수 없다. 이번
변경으로 400줄 규모가 되므로 재구성한다.

핵심 경계는 **네트워크에 닿는 코드와 순수 계산 코드를 가르는 선** 하나다.

```
news-app/
  fetch_news.py        오케스트레이션 + 카테고리 설정        ~60줄
  news/
    sources.py         Google·Naver 수집 (외부 호출 전부)    ~120줄
    rank.py            정규화·클러스터링·채점·선출           ~180줄
                       네트워크 없음. 전부 순수 함수.
    history.py         노출 이력 저장/조회                   ~40줄
  tools/
    measure_rotation.py  회전율 측정 (git 이력에서 계산)
  tests/
    test_rank.py
    test_sources.py
```

### 데이터 계약

모듈 사이를 오가는 타입은 둘뿐이다.

```python
Article
    title      str
    link       str        정규화됨 (쿼리스트링 제거)
    published  datetime
    outlet     str        언론사명
    origin     str        'google' | 'naver'
    rank       int        소스 내 순위 (0-based)

Cluster
    articles   list[Article]
    origins    set[str]   교차 점수의 근거
    outlets    set[str]   매체폭의 근거
    best_rank  int        클러스터 내 최고(최소) 순위
    newest     datetime   가장 최근 발행 시각
```

`rank.py`는 `Cluster`만 알면 되고 Google/Naver가 무엇인지 몰라도 된다. 따라서 실제
API 호출 없이 손으로 만든 클러스터로 채점 로직 전체를 테스트할 수 있다.

### 흐름

```
config (fetch_news.py) — 카테고리 하나
        ↓
sources.py — Google + Naver 각자 수집 (서로 모름)
        ↓
rank.py — 정규화 → 클러스터링 → 채점 → 대표 선출
        ↓        (history.py에서 노출 이력 조회)
fetch_news.py — news_data.json + seen_history.json 저장
```

`cat-etc`는 같은 흐름을 타되 `sources.py`가 Naver를 *수집* 대신 *검증* 모드로
호출한다. `rank.py` 이하는 차이를 모른다.

## 5. 채점

### 신선도 (0~100)

```
신선도 = 100 × 0.5^(경과시간_시간 / 6)
```

경과시간은 `Cluster.newest` 기준. 후속 보도가 붙는 사건은 신선하게 유지되고, 멎은
사건은 가라앉는다.

| 경과 | 0h | 1h | 3h | 6h | 12h | 24h |
|---|---|---|---|---|---|---|
| 점수 | 100 | 89 | 71 | 50 | 25 | 6 |

24시간 기사는 6점이므로 검색 창(`when:1d`)을 좁힐 필요가 없다. 창을 넓게 두면 후보
풀만 커지고 손해가 없다.

### 중요도 (0~100)

```
중요도 = 교차(40) + 순위(35) + 매체폭(25)

교차   = 40 if 'google' in origins and 'naver' in origins else 0
         (cat-etc: Naver 유사 기사 3건 이상이면 40)
순위   = max(0, 35 × (1 − best_rank / 20))
매체폭 = 25 × clamp(len(outlets) − 1, 0, 4) / 4
```

| 언론사 수 | 1 | 2 | 3 | 4 | 5+ |
|---|---|---|---|---|---|
| 매체폭 점수 | 0 | 6 | 13 | 19 | 25 |

두 공식 모두 하한을 0으로 고정한다. `best_rank`가 20을 넘거나(Naver `display`를
20보다 크게 잡은 경우) `outlets`가 비면 음수가 나오기 때문이다.

cat-etc의 "유사 기사 3건 이상"에서 3은 **근거 없는 초기값**이다. 배포 후 실제
분포를 보고 조정한다. 나머지 4개 카테고리의 교차 판정은 이 임계값과 무관하다.

### 총점

```
총점 = 0.5 × 신선도 + 0.5 × 중요도 − 이력감점
이력감점 = min(노출횟수 × 12, 60)
```

### 검산 (2026-08-11 관측 사례)

기사 제목·순위·노출 횟수는 실측값이다. **발행 경과 시간과 Naver 교차 여부는
가정값**이다 (당시 Naver를 호출하지 않았으므로 확인할 수 없다). 공식이 의도한
방향으로 작동하는지 보기 위한 예시이며, 실제 검증은 §8의 회귀 테스트와 §9의
배포 후 측정으로 한다.

| | 국힘 "주거지옥" 논평 | 서울 집값 15% 급등 |
|---|---|---|
| 신선도 | 6시간 전 → 50 | 2시간 전 → 79 |
| 교차 | Naver 없음 → 0 | 양쪽 → 40 |
| 순위 | Google 3위 → 30 | Google 1위 → 35 |
| 매체폭 | 1곳 → 0 | 8곳 → 25 |
| 중요도 | 30 | 100 |
| 총점(감점 전) | 40 | 90 |
| 이력 | 11회 → −60 | 1회 → −12 |
| **최종** | **−20 (탈락)** | **78 (채택)** |

### 노출 이력은 기사 링크 기준

사건(클러스터) 기준이 아니라 **기사 링크 기준**으로 센다. 이 차이가 동작을 가른다.

- 후속 보도 없이 같은 기사만 반복되는 경우 (cat-coin "호주 ATM 중단", 12회 연속)
  → 해당 링크에 감점이 누적된다. 5회 노출이면 감점이 상한(60)에 도달한다.
- 계속 전개되는 큰 사건 → 새 기사가 유입되고 그 기사의 이력은 0이다.
  **사건은 남고 헤드라인만 바뀐다.**

클러스터 기준으로 감점했다면 대형 사건도 강제로 사라졌을 것이다.

**감점은 탈락을 보장하지 않는다.** 실제로 밀려나는 시점은 경쟁 클러스터의 점수에
달려 있다. 감점 상한이 60이므로, 신선도·중요도 합계가 60을 크게 웃도는 사건은 계속
살아남는다 — 이는 의도된 동작이다. 정말 압도적인 뉴스를 인위적으로 밀어내지 않는다.

### 대표 기사 선출

클러스터 안에서 다음 순서로 고른다.

1. 노출 이력이 적은 것
2. 더 최신
3. Naver `originallink`(원문 URL) 우선

3번은 Google 뉴스 링크(`news.google.com/rss/articles/…` 리다이렉트)의 404 이력에
대한 대비다.

## 6. 예외 처리

| 상황 | 동작 |
|---|---|
| Naver만 실패 | Google 단독 진행. 모든 클러스터의 교차 점수가 0이 되어 순위·매체폭으로 공정 경쟁 |
| Google만 실패 | Naver 단독 진행. 동일 |
| 둘 다 실패 | **이전 `news_data.json`의 해당 카테고리 유지.** 빈 배열로 덮어쓰지 않는다 |
| 카테고리 간 | 독립. 하나 실패해도 나머지 진행 (현행 유지) |

현행은 카테고리 실패 시 빈 배열을 저장해 앱에 "뉴스를 불러올 수 없습니다"가 뜬다.
이전 데이터 유지로 개선한다. 이를 위해 `fetch_news.py`는 저장 전에 기존
`news_data.json`을 읽는다.

어느 카테고리에서 어느 소스가 빠졌는지를 `news_data.json`에 기록한다.

```json
"degraded": { "cat-coin": ["naver"], "cat-land": ["google", "naver"] }
```

화면(`index.html`)은 이번 작업에서 변경하지 않는다 — 원인 추적용 데이터만 남긴다.

Naver API 429(호출 초과)에 대비해 **1회 재시도 + 백오프**를 둔다. 일일 한도와는
무관하고 순간 속도 제한에 대한 대비다.

## 7. 노출 이력 파일

```json
{
  "https://example.com/article/123": {
    "count": 3,
    "last": "2026-08-11T12:00:00Z"
  }
}
```

- 48시간 지난 항목 삭제
- 예상 크기: 최대 600개 항목, 약 70KB. `news_data.json`과 함께 커밋
- **링크 정규화 필수.** 같은 기사가 `?ref=naver` 같은 꼬리를 달고 오면 다른 링크로
  세어져 감점이 누적되지 않는다. 쿼리스트링을 제거하고 저장한다

## 8. 테스트

`rank.py`가 순수 함수이므로 네트워크 없이 전부 실행된다.

**tests/test_rank.py**
- 신선도 감쇠 경계: 0h=100, 6h=50, 12h=25
- 교차 점수: google+naver=40, 한쪽만=0
- 순위·매체폭 경계값
- 이력 감점 상한: 7회 노출해도 60에서 멈춤
- 클러스터링: 같은 사건 묶임 / 다른 사건 안 묶임
- 대표 선출 우선순위: 이력 → 최신 → Naver 원문
- **회귀 시나리오**: 2026-08-11 실제 데이터를 픽스처로 고정.
  "국힘 논평"이 지고 "집값 15% 급등"이 이기는지 검증

**tests/test_sources.py**
- 저장된 RSS/JSON 응답으로 파싱 검증 (네트워크 없음)
- 404를 유발했던 guid-only 케이스 포함
- Naver 예외 발생 시 Google 단독 결과가 나오는지

회귀 시나리오가 핵심이다. 관찰된 실패 사례를 테스트로 고정하면 이후 숫자 튜닝
과정에서 깨질 때 즉시 알 수 있다.

3. `.github/workflows/fetch_news.yml`에 해당 env 추가

키는 Cloudflare `wrangler secret`으로만 저장되어 있어 되읽을 수 없다. Naver
개발자센터에서 직접 확인해야 한다.

**신규 발급이 아니라 기존 키 재사용이어야 한다.** 맛집 큐레이션 워커가
`/v1/search/blog.json`을 사용하므로 해당 앱은 '검색 API' 권한으로 등록되어 있고,
뉴스 검색(`/v1/search/news.json`)은 같은 검색 API의 하위 유형이라 추가 신청 없이
동작한다. 자세한 배경은 §11 참조.

## 11. 네이버 API 이관 리스크

2026-08-11 확인. 네이버 개발자센터가 API 3종을 NAVER Cloud Platform의 NAVER API
HUB로 이관하며 단계적으로 종료한다. **이관 대상에 Search API(검색 API)가 포함된다.**

이관 대상: Search API, Search Trend API, Shopping Insight API

| 단계 | 일정 | 내용 |
|---|---|---|
| 1 | 2026-06-25 | NAVER API HUB 정식 출시 |
| 2 | **2026-07-31** | **개발자센터에서 3종 신규 신청 차단 (이미 경과)** |
| 3 | **2027-06-30** | **개발자센터 지원 종료. 기존 발급 키도 차단** |

2026-07-31 이전 신청한 키는 2027-06-30까지 개발자센터에서 사용 가능하다.

### 이 설계에 미치는 영향

**신규 신청 차단일이 이미 지났다.** 뉴스앱용으로 개발자센터에 새 앱을 등록하는
것은 불가능하다. 따라서 맛집 큐레이션의 기존 키를 공유하는 것이 유일한 무료 경로이며,
이 설계는 그 전제로 작성되었다.

### 채택한 방침

**기존 키를 그대로 쓴다.** 2027-06-30까지 하루 25,000회 무료로 동작한다.

API HUB로 지금 이관하는 안은 채택하지 않았다. 이유:

- API HUB의 무료 쿼터 규모가 공지에 명시되지 않았다. 현재 확정된 25,000회/일을
  버릴 근거가 없다
- 공지에 "한시적으로 무료 요금제로만 지원하며 추후 유료 요금제를 제공할 계획"이라고
  되어 있다. 조건이 나온 뒤 판단하는 편이 낫다
- NCP 계정을 새로 만들어 관리해야 한다
- 구현·검증이 먼저다. 동작 여부도 확인 안 된 설계를 위해 클라우드 계정을 만들 이유가 없다

### 기한 관리

**2027-06-30까지 이관 필요.** 대상은 뉴스앱과 맛집 큐레이션 두 곳이다.
맛집 큐레이션은 현재 운영 중인 서비스이므로 함께 계획해야 한다.

이관 시 변경 사항은 인증 체계(개발자센터 Client ID/Key → API HUB Client ID/Key)와
호스트뿐이다. `sources.py`에 국한되며, 채점·클러스터링 로직은 영향을 받지 않는다.
소스 접근을 한 파일로 격리한 이유 중 하나가 이것이다.

### 대안 (네이버가 유료화되거나 조건이 나빠질 경우)

두 번째 소스를 **언론사 자체 RSS**(연합뉴스, 한국경제, 매일경제 등)로 교체한다.
API 키가 필요 없고 기한도 없다. 언론사 RSS 상단은 해당 매체 편집자가 직접 톱으로
올린 기사이므로, 검색 알고리즘의 정확도순보다 "중요도"라는 측정 대상에 오히려 더
가까울 수 있다. 다만 매체별 RSS 형식이 제각각이고 부동산·코인 전문 매체 커버리지가
약하다.

교차 검증·클러스터링·채점 공식은 소스가 무엇이든 그대로 동작한다. 교체 범위는
`sources.py` 한 파일이다.

## 12. 범위 밖 (의도적 제외)

- **사설·칼럼 제목 접두사 감점.** 교차 검증이 이미 이 역할을 한다(사설은 다른 매체가
  받아쓰지 않아 교차 점수 0). 배포 후 24시간 관찰해서 여전히 사설이 상위에 오면
  그때 추가한다.
- **AI 요약 / AI 중요도 판정.** 별도 작업으로 분리.
- **화면(index.html) 변경.** 이번 작업은 수집·랭킹에 한정한다.
- **cron 주기 변경.** GitHub Actions 스케줄 지연은 통제 불가.
- **검색 창 축소(`when:1d` → `12h`).** 신선도 감쇠가 같은 일을 하므로 불필요.
